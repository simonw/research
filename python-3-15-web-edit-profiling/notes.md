# Investigation notes: Python 3.15 profiling web-edit

## 2026-10-12 — Initial research and experiments

These notes summarize the profiler experiments completed earlier in this session, then track packaging the results for simonw/research. The user clarified that the second requested visualization was a source-code heatmap, not a heap-memory profile.

- Queried PyPI's JSON API and inspected the installed `web-edit==0.1a0` wheel. Its CLI is `web_edit.cli:cli`; the server factory is `web_edit.app.create_app`. Its dependencies include Starlette, Uvicorn, Click, and python-multipart.
- Confirmed the installed interpreter is CPython 3.15.0 on macOS 26.4 ARM64. Its `profiling` package contains `sampling` and `tracing`; `profiling.sampling` exposes binary recording, replay, flame graphs, source heatmaps, CPU mode, and all-thread sampling.
- Inspected `web_edit/app.py` and `web_edit/files.py`. File handlers execute in AnyIO worker threads. `FileStore.save_text` calls `preserve_endings`, which uses `difflib.SequenceMatcher` to retain original line endings. This suggested a large-document edit workload and sampling all threads.
- An initial native-profiler smoke test failed with macOS process-memory access denied. Copied the uv-managed interpreter into this project's `.venv/bin/python-profile` and ad-hoc signed that private copy with `com.apple.security.get-task-allow` and `com.apple.security.cs.debugger`. Profiling then worked without sudo or changing the system interpreter.
- Built a loopback-only Uvicorn harness and a separate HTTP load generator. The fixture contains a 12,000-line UTF-8 document with mixed LF/CRLF endings and 800 small files. Each cycle browses, reads, edits and saves, downloads, uploads, and deletes. Requests validate status codes, saved content, SHA-256 versions, preserved CRLF, and deletion responses.
- The first integration run failed because the profiler's duration parser requires an integer; changed the runner's `--seconds` argument from float to int. A later validation falsely expected full package paths in collapsed stacks; changed it to check the actual `FileStore.save_text` and `preserve_endings` frame names.
- Warmed the app with one editing cycle before attaching. Recorded only the server PID with all-thread CPU sampling; client and fixture-generation work remain outside the sampled process.
- The delivery recording ran for 20 seconds at a requested 1 kHz. It contains 15,296 recorded stack samples, while the capture log reports 20,000 sampling attempts and a 13.40% error rate. The overlapping client session completed 389 cycles / 3,112 successful HTTP requests. No extrapolation from failed samples was attempted.
- Replayed the same binary into a flame graph and a 45-file source heatmap. Aggregating collapsed stacks by presence of a function gives 77.0% for `FileStore.save_text`, 64.8% for `preserve_endings`, 38.3% for `SequenceMatcher.find_longest_match`, and 7.5% for `FileStore.browse`. These inclusive percentages overlap.
- Inspected the reports in the browser. Flame graph search highlights the save path; the source heatmap's total-time view and hot-line filtering expose expensive call sites. No browser errors were reported in the inspected view.
- Observed a native replay limitation: the heatmap index shows zero duration/rate and unavailable collection diagnostics. Its source samples are present, and the flame graph and capture log show the actual collection timing. Also observed that cumulative per-file heatmap counts count more than one frame per stack and should not be interpreted as disjoint sample percentages.
- Verified binary replay, local report links, absence of client frames, clean server logs, server shutdown, lint, and formatting.
